# Telegram Gateway

Private Telegram account gateway designed to expose controlled, read-only Telegram data to MCP clients and other API consumers.

## Current architecture

```text
Telegram / TDLib (planned)
        |
        v
Telegram sync workers
        |
        +---- PostgreSQL  <- chats, messages, sync state, audit
        |
        +---- MinIO       <- media objects
        |
        +---- Redis       <- rate limits, cooldowns, short-lived cache
        |
        +---- NATS        <- sync/event jobs
        |
        v
Gateway API
        |
        v
MCP server (planned)
```

## Core rules

- MCP starts read-only.
- Telegram limits are protected by our own stricter rate limits before TDLib requests are sent.
- Synced chats and messages are persisted in PostgreSQL so repeated AI analysis does not repeatedly hit Telegram.
- Telegram-deleted records are soft-deleted with `deleted=true` and retained in storage.
- Normal API/MCP reads must use the active projections and never return soft-deleted records.
- Media is stored in MinIO and referenced by PostgreSQL records.
- Security/access events are written to append-only audit logs. Hash chaining is generated by the application layer.
- TDLib session material must never be committed to Git and will be encrypted before production use.

## Stack

- Go 1.27.1
- PostgreSQL 18.x
- Redis 8.2.x
- NATS JetStream 2.14.x
- MinIO-compatible object storage
- TDLib for Telegram user accounts (next stages)
- Official MCP Go SDK (next stages)

## Local development

Create local configuration:

```bash
cp .env.example .env
```

Change all development passwords in `.env`, then start infrastructure:

```bash
make infra-up
```

Apply the core schema:

```bash
make migrate-up
```

Run the API locally:

```bash
make run
```

Health endpoints:

```text
GET /health/live
GET /health/ready
```

`/health/live` only reports process liveness. `/health/ready` checks whether PostgreSQL, Redis, NATS, and MinIO are reachable.

## Data model

The first migration creates:

- `app_users`
- `telegram_accounts`
- `chats`
- `messages`
- `message_media`
- `sync_states`
- `audit_logs`
- `active_chats` view
- `active_messages` view

`messages` and `chats` are intentionally soft-deleted. `audit_logs` rejects SQL `UPDATE` and `DELETE` operations through database triggers.

## Planned implementation order

1. Infrastructure clients and database repositories.
2. Audit writer with tamper-evident hash chain.
3. Authentication, API tokens and read scopes.
4. Redis token-bucket rate limiter and Telegram cooldown model.
5. NATS JetStream sync jobs.
6. MinIO media service.
7. TDLib account authentication/session lifecycle.
8. Telegram chat/message incremental + historical sync.
9. Read-only REST API.
10. Read-only MCP tools and OAuth authorization.
11. Security review, load tests and production hardening.

The TDLib lifecycle, session encryption, distributed account ownership and MCP authorization layers are intentionally left until the stable foundation is complete.
